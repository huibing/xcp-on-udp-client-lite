# New web ui page -> Experiment

This is a develop guideline for a new web ui page: Experiment. This page is designed for users to start a new experiment, which includes variable selection, DAQ process control, calibration and data recording.

## Page content

This new experiment page should have the following content:
1. A title to indicate the name of this experiment which can be easily changed by user.
2. A button to invoke a variable selection dialog, note that all variables could be selected including *** both  measurements and parameters from  ALL SLAVES *** not just one slave. The dialog uses a **flat list with filters/search** — checkboxes to select variables, with filters for slave name, variable type (measurement/parameter), and name search.
3. A start button to start the DAQ process. After user clicks the start button, this button becomes to a recording button, so that user can click it again to record the data to a mf4 file.
4. A stop button to stop the DAQ process.
5. A switch to switch reference and working page of calibration. This is a **global switch** that applies to all connected slaves at once. If a slave fails to switch, an error is shown and the remaining slaves continue switching. **Important:** If a slave fails to switch to working page, all its calibration variables become **read-only** — the user cannot edit them until the page switch succeeds.
6. The main page area contains a multiple tabs editor (like vscode editor, each tab has its own code editor), each tab contains calibration and measurements variables selected by user. Each tab should have a title, which is auto-generated by the program but can be edited by user. Each tab should have a close button, so that user can close the tab if they want.
7. Each tab's measurement variables and calibration variables are displayed using a **card-based layout** — each variable is shown as a small card displaying name + current value (+ unit if available). Measurements are display-only; calibration variables are editable only in working page mode. Map and curve calibration variables are displayed in a **separate section** of the tab using **editable table views** (graphical visualization deferred to future improvements). All variables can be removed from the experiment easily by user.
8. A connection button to connect to the slave, which **reuses the existing connect page/flow** (opens in a modal or redirects to the existing /connect page). After connection, the variable list is fetched. Also a status bar to display all the slave connection status, and their a2l name etc.
9. A save button to save the experiment configuration, including each tab's variable selection, calibration settings and tab settings. The configuration is saved as **JSON format, downloaded to the user's browser** as a client-side file download. **Save as much information as possible** about the experiment for later development and features, including: tab names, variable selections per tab, slave connection info (addresses, A2L paths, custom names), calibration page mode, experiment title, config settings, and any other state that could be useful for restoring or extending the experiment later.
10. A load button to load the experiment configuration, which can be used to continue the experiment or start a new experiment with the same configuration. After user clicks this button, a **browser file picker dialog** opens to let user select a JSON configuration file from their local machine. After user selects the file, the program will parse and load the configuration and update the page accordingly.
11. A checksum verification button to verify the checksum of all connected slaves. Results are displayed in a **modal dialog** showing pass/fail status per slave.
12. A add tab button to add a new tab in the main page area, so that user can organize their variables in different tabs. Each tab can be used for different purpose, such as one tab for engine variables, one tab for transmission variables, etc. This allows users to keep their experiment organized and easy to navigate.
13. A **config button** to open an experiment-wide configuration dialog. This allows users to configure settings such as:
    - MF4 output file naming pattern
    - A2L file associations (add/manage A2L files per slave)
    - Slave transport configuration (UDP address/port, etc.)
    - Other experiment-level settings as needed in the future
14. Users can **rename any slave** with a custom display name to help distinguish between slaves (e.g., "Engine ECU", "Transmission ECU"). The custom name is shown throughout the Experiment page and saved with the experiment configuration.

### State Machine (Start / Record / Stop)

The DAQ control follows a simple linear state machine:
- **Idle** → click **Start** → DAQ begins on all slaves that have selected measurements (started simultaneously) → button changes to **Record**
- **DAQ Running** → click **Record** → MF4 recording begins → button shows recording indicator
- **Recording** or **DAQ Running** → click **Stop** → both DAQ and recording stop together → back to **Idle**

Stop always stops both DAQ and recording together — there is no way to stop recording independently while keeping DAQ running.

MF4 output filename is **auto-generated** using: `{experiment_title}_{YYYYMMDD}_{HHMMSS}.mf4`

### Page Coexistence

This Experiment page **coexists alongside** the existing separate DAQ and Calibration pages as a new menu item. The old pages are **not deleted**, but when an experiment is selected and activated (DAQ started), the DAQ and Calibration pages are **disabled** (greyed out / inaccessible) to prevent conflicts with the experiment's DAQ and calibration state. They become accessible again once the experiment is stopped.

## Page layout
The layout of this new experiment page should be designed in a way that is user-friendly and easy to navigate. 
Use a layout like vscode.

### Title
The title should be placed at the top of the page. 

### Control buttons
The control buttons (variable selection, start/record, stop, switch reference/working page, connection, save, load) should be placed below the title, in a toolbar or a button group. 
Like vscode, the control buttons can be placed in a vertical toolbar at the top of the page, below the title. This allows users to easily access the controls while working on their experiment.
These buttons should have clear icons to indicate their functions, and tooltips to provide additional information when users hover over them.

### Main page area
The main page area should be designed to accommodate the multiple tabs editor. 
Like vscode, the main page area align horizontally with the control buttons, allowing users to easily switch between different tabs while keeping the controls accessible. Each tab should have a clear title and a close button, and the content of each tab should be organized in a way that is easy to read and understand.

### Status bar
The status bar should be placed at the bottom of the page, displaying the connection status of all slaves, their a2l names, and any other relevant information. This allows users to quickly check the status of their connections without having to navigate away from the main page area. Keep the status bar content simple and concise, if string is too long, we can use tooltip to show the full content when user hover over it.
Remeber, this is a draft requirements, so later we may need to update the status bar with new contents.


## Implementation details
This new experiment page should use existing http api to control the DAQ process/calibration process as much as possible, so that backend develop is minimal. 

### Architecture

- **Frontend**: Single `experiment.hbs` template with all JS inline (matching existing pattern). No new JS frameworks.
- **Backend**: New `experiment_page` route + a handful of new API endpoints for multi-slave orchestration. Experiment state lives mostly in JavaScript (client-side) since save/load is browser-based JSON. Only an `experiment_active` flag on the server to disable DAQ/Cal pages.
- **State Machine**: JS-managed experiment state (`idle` / `running` / `recording`) controls button visibility and variable selection locking.
- **MF4**: Reuse existing recording infrastructure with per-event CG/DG structure.

### New Backend Endpoints

| Endpoint | Method | Purpose |
|----------|--------|---------|
| `/experiment` | GET | Serve experiment page |
| `/api/experiment/variables` | GET | Get ALL variables (measurements + calibration) across ALL devices |
| `/api/experiment/start` | POST | Start DAQ on multiple slaves simultaneously |
| `/api/experiment/stop` | POST | Stop DAQ on all slaves |
| `/api/experiment/record/start` | POST | Start MF4 recording with experiment title in filename |
| `/api/experiment/record/stop` | POST | Stop MF4 recording |
| `/api/experiment/status` | GET | Get DAQ + recording status across all slaves |
| `/api/experiment/pagemode` | POST | Switch cal page mode on all slaves (global switch, return per-slave success/failure) |
| `/api/experiment/rename-slave/:device_id` | POST | Rename a slave's display name |
| `/api/experiment/checksum` | POST | Run checksum verification on all connected slaves |

### Reusable Existing Endpoints

| Endpoint | Used For |
|----------|----------|
| `/api/cal/read/:device_id/:idx` | Read individual cal parameter |
| `/api/cal/write/:device_id/:idx` | Write individual cal parameter |
| `/api/cal/write-element/:device_id/:idx` | Write single matrix element |
| `/api/cal/value/:device_id/:idx` | Get cached cal value |
| `/api/cal/detail/:device_id/:idx` | Get cal parameter detail |
| `/api/daq/data` | Poll latest DAQ sample |
| `/api/daq/detail/:device_id/:idx` | Get measurement detail |
| `/api/devices/connect-all` | Connect all configured devices |
| `/api/devices/connect` | Connect a specific device |

### Pitfalls
Some details of the implementation should be carefully designed to avoid potential pitfalls, such as:
1. When user click the start button, all **unique** measurement variables across all tabs will be collected and DAQ will be started on **all relevant slaves simultaneously**. Each slave only receives the measurements that belong to it. User can see real-time data of all variables in all tabs. 
2. When user click the recording button, all variables in all tabs will be recorded to the mf4 file, so that user can analyze the data later. Filename is auto-generated: `{experiment_title}_{YYYYMMDD}_{HHMMSS}.mf4`. **MF4 structure:** Each slave's each DAQ event gets its own Channel Group (CG) within its own Data Group (DG). For example, if 6 events are selected from 3 slaves, 6 CGs are created each with its own DG.
3. When user click the stop button, the DAQ process will be stopped on **all slaves**, and all variables in all tabs will be removed from the DAQ process, so that user can start a new experiment or continue the current experiment with different variables.
4. In started or recording state, user can not change the variable selection, but can switch reference/working page of calibration and edit the calibration variables in working page.
5. One measurement variable can be added to multiple tabs, but it will only be added to the DAQ process once, and recorded to the mf4 file once, so that we can avoid duplicate data in the DAQ process and mf4 file.
6. One calibration variable can be added to multiple tabs. Once the user edit the calibration variable in one tab, the change will be reflected in all tabs that contain this calibration variable, so that we can keep the calibration variable consistent across all tabs. 
7. Program should at least support 20 tabs. If user try to add more than 20 tabs, a warning message should be displayed to inform user that they have reached the maximum number of tabs. This is to prevent the program from becoming too slow or unresponsive due to too many tabs.


### Future improvements
In the future, we can consider adding more features to this experiment page, such as:
1. A data visualization section to display the real-time data of the selected variables in a graphical format, such as line charts or bar charts.
2. A data analysis section to provide basic data analysis tools, such as statistical analysis or data fitting, to help users analyze their experiment data.
3. Calculation of derived variables based on the selected measurement variables, which can be displayed in the tabs and recorded to the mf4 file.
4. In tab editor, user can customize the layout of the variables, such as grouping variables into different sections, or changing the order of the variables. This allows users to organize their variables in a way that is most convenient for them.
